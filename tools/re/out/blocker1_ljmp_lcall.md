# Blocker 1 analysis: LJMP / LCALL addressing

## Verdict

The misdecoded ops are **true MCS-96 `LJMP` (`E7`) and `LCALL` (`EF`)** with a **16-bit PC-relative displacement**.

| Claim | Result |
|-------|--------|
| Different opcode / not LJMP? | **No** — Intel opcode map `E7=LJMP`, `EF=LCALL` |
| Absolute destination word? | **Rejected** — that was our offline misread |
| Toolchain quirk vs Intel? | **No quirk** — matches Intel MCS-96 assembler semantics |
| Stock Ghidra SLEIGH bug? | **No** — `inst_next + disp16` is correct |

**Fix applied:** stop rewriting targets as absolute; emit PC-relative CFG edges (`mcs96_cfg_edges.*`) that cross-check Ghidra (**385/385** aligned sites match).

## Intel reference

MCS-96 Macro Assembler User’s Guide (LJMP / LCALL):

- Encoding stores **offset from the end of the instruction**
- Operation: `PC ← PC + disp` (LCALL also pushes return PC)
- Opcodes: `E7 disp_lo disp_hi` / `EF disp_lo disp_hi`

Formula used offline:

```text
target = (insn_addr + 3 + le16(disp_lo,disp_hi)) & 0xFFFF
```

Computation example (`0x2094`):

```text
bytes     = E7 7B 16
disp      = LE16(7B,16) = 0x167B
target    = 0x2094 + 3 + 0x167B = 0x3712
abs-wrong = 0x167B  (erased low image — not a plausible handler)
```

## Why absolute looked tempting (and failed)

| Metric (Ghidra-aligned LJMP/LCALL) | PC-rel (correct) | Abs LE16 (rejected) |
|------------------------------------|------------------|---------------------|
| Targets in CODE window | **349** | 46 |
| Targets in PAD_LOW (erased) | 0 | **159** |
| Targets in DATA | 36 | 180 |
| Match Ghidra listing operand | **385 / 385** | ~0 |

Absolute targets from the `0x2094` trampoline table fall into `0x0000–0x1FFF` (all `0xFF` in this external dump). PC-rel targets land on real prologues (`LD SP`, `CLRB`, `JBC`, …).

## IRQ stubs note (not an encoding issue)

Vector table `@0x2000` → 4-byte stubs at `0x4178 + 4*n` (`PUSHF`/`NOP` + `LJMP`).  
PC-rel destinations for several stubs land in **high image `0xAxxx`** (labeled DATA_CAL by region map). That is a **memory-map / code-in-cal follow-up**, not evidence for absolute addressing — encoding still matches `PC + disp`.

## Fix path chosen

| Option | Decision |
|--------|----------|
| Patch Ghidra SLEIGH to absolute | **Do not** — would break Intel-correct CFG |
| Post-process absolute overlay | **Rejected** — prior `mcs96_absolute_branches.*` deprecated |
| PC-rel CFG export + Ghidra cross-check | **Implemented** |
